Я бы делал это как небольшое macOS desktop-приложение на .NET с Avalonia UI. Оно будет работать как локальный диспетчер LLM: обнаруживать два сервера, показывать их состояние, находить модели в заданной папке и запускать выбранную модель на нужном сервере.

Должно быть в TrayIcon и по клику вызывать меню как в примере интерфейса


## 1. Что будет делать приложение

Local LLM Manager

Пример интерфейса
```
**LLM Servers**
- *llama.cpp* 127.0.0.1:4901 (Working)
- *MLX-LM* 127.0.0.1:4902 (stopped)


**Models**
* Qwen3-Coder-30B-A3B - Loaded
* Cyber-Tiel-Coder-35B - Available
* Llama-3-8B - Available

[Load Model]
[Stop server]
[Quit]
```

Основные функции:

1. Автоматически проверять, какие серверы запущены.
2. Показывать адрес, порт и текущую модель.
3. Сканировать выбранную папку с моделями.
4. Определять формат модели: MLX или GGUF.
5. Показывать модели, подходящие для каждого сервера.
6. Запускать выбранную модель.
7. Останавливать сервер и переключать модель.
8. Хранить настройки между запусками приложения.

## 4. Как обнаруживать работающие серверы

Я бы не ограничивался проверкой процессов через `ps`.

Лучше использовать два механизма:

Первый — HTTP-проверка.

```
curl http://127.0.0.1:4901/v1/models
curl http://127.0.0.1:4902/v1/models
```

Приложение проверяет `/v1/models` через `HttpClient` и разбирает JSON-ответ. Ответ с моделью в поле `data` означает, что модель загружена; в этом случае значок в системном трее становится зелёным. Команды `curl` выше приведены только как примеры ручной проверки.

Второй — управление процессами.

Если сервер не запущен, приложение само запускает его через `System.Diagnostics.Process`.

Важно: если сервер уже запущен пользователем вручную, приложение обнаруживает его, но не считает своим процессом. На macOS пункт «Stop external server» определяет PID слушателя настроенного порта, сверяет команду запуска с настроенным исполняемым файлом и посылает этому процессу SIGTERM. Несовпадающий процесс не останавливается.

## 5. Сканирование папки моделей

В настройках пользователь выбирает директорию, например:

```
/Users/alexsid/AI/
```

Сканер должен находить:

```
Models/
├──── model-Q6_K.gguf
│
├── Cyber-Tiel-MLX/
│   ├── config.json
│   ├── model.safetensors
│   └── tokenizer.json
│
└── Another-Model/
    └── model.gguf
```

Здесь есть нюанс: MLX-модели часто представляют собой директории с несколькими файлами, а GGUF — отдельные файлы. Поэтому сканировать нужно рекурсивно, но не считать каждый `.safetensors` отдельной моделью.

Я бы добавил внутреннюю модель данных:

```
public record ModelInfo(
    string Name,
    string Path,
    ModelFormat Format,
    long SizeBytes
);

public enum ModelFormat
{
    Mlx,
    Gguf,
    Unknown
}
```

При этом `ModelFormat` будет определять совместимость с сервером.

## Реализованный MVP

Приложение запускается в системном трее. В меню доступны выбор и повторное сканирование папки, состояние серверов, запуск совместимой модели, остановка процесса, запущенного приложением, и выход. Названия моделей отображаются только как `имя (GGUF)` или `имя (MLX)`, без полного пути, размера и дополнительной информации о файлах. Пункт **Current Status** после **Models folder** содержит адреса работающих серверов, имена известных загруженных моделей, параметры (размер контекста и температуру) и текущее сообщение статуса; каждый пункт можно скопировать в буфер обмена. Для работающего `llama.cpp` доступны ссылки **Open server**, **Open model** (`/v1/models`) и **Open params** (`/props`); при остановленном сервере они отключены. Для внешнего сервера ID модели берётся из `/v1/models`, а runtime-параметры llama.cpp — из `/props`; неизвестные значения не подменяются локальными настройками. Для запущенных приложением моделей используются параметры, переданные при запуске. Размер контекста отображается сокращённо (например, `30k`), а при копировании попадает точное число. Если работающих серверов или известных параметров нет, соответствующий пункт копирования отключён. MLX-модель определяется по `config.json` и `.safetensors` в одной папке; GGUF — по файлам `.gguf`.

Набор серверов фиксирован: MLX-LM и llama.cpp создаются при запуске приложения и не добавляются или удаляются динамически. Меню сервера строится для этого набора.

При старте приложение сканирует сохранённую папку моделей и обновляет состояние серверов. Статус сервисов обновляется при клике по значку в трее (на платформах, где Avalonia поддерживает это событие) и при открытии меню; периодического обновления по таймеру нет. Выбранная папка моделей сохраняется атомарно между запусками в `settings.json` в каталоге `LmManager` внутри `Environment.SpecialFolder.ApplicationData`; точный путь к файлу настроек указывается в логе приложения. Там хранятся также папка логов, адреса и порты серверов и команды запуска. Логи пишет Serilog в `lm-manager.log` с прокруткой при достижении 1 MB и хранением не более пяти файлов. Для каждого сервера приложение проверяет настроенный executable, затем ищет его имя в `PATH`; на macOS также проверяются стандартные каталоги Homebrew (`/opt/homebrew/bin` и `/usr/local/bin`), поскольку приложения, запущенные из Finder, могут не получить shell `PATH`. На Unix проверяются права на выполнение, а при запуске сообщается об ошибках формата файла, разрешений или runtime. Если команда не найдена, укажите абсолютный путь в `~/Library/Application Support/LmManager/settings.json`. Формат аргументов запуска:

При запуске на macOS каталог `/opt/homebrew/bin` добавляется в начало `PATH`, если он существует и ещё не добавлен.

- MLX-LM: `mlx_lm.server --model <путь> --temp <temperature> --host <host> --port <port>`
- llama.cpp: `llama-server -m <путь> --ctx-size <context size> --temp <temperature> --host <host> --port <port>`

Для каждой модели GGUF размер контекста задаётся в меню модели и сохраняется в `settings.json` по пути к модели. По умолчанию используется 131072 токена (128K); доступны значения: 32768, 65536, 131072. Параметр передаётся llama.cpp как `--ctx-size`. Для MLX значение сохраняется отдельно для модели, но не передаётся серверу: MLX-LM не предоставляет эквивалентного параметра размера контекстного окна.

Температура настраивается отдельно для каждой модели GGUF и MLX в меню модели и сохраняется по пути к модели. В меню доступны пресеты `Development (0.3)`, `Analytics (0.5)`, `Regular (0.7)` (по умолчанию) и `Creative (0.9)`; значение передаётся соответствующему серверу через `--temp`.

Состояние проверяется через OpenAI-compatible endpoint `/v1/models`. Ручные процессы обнаруживаются; на macOS их можно остановить из меню соответствующего сервера, если команда процесса совпадает с настроенным исполняемым файлом. Управляемый процесс завершается при выборе другой модели или выходе из приложения.

## macOS: запуск, публикация и подпись

В VS Code используйте конфигурацию **Launch published macOS app** для сборки и запуска локального `.app` bundle. Задача **Publish macOS app** создаёт self-contained Apple Silicon bundle в `artifacts/macos/LLM Manager.app`. Задача **Sign macOS app** сначала публикует приложение, затем подписывает его. Для подписи требуется установленный в Keychain сертификат Apple Developer ID Application; при запуске задачи введите его полное имя. Учётные данные не хранятся в проекте. Задача подписывает приложение, но не выполняет нотариализацию.
